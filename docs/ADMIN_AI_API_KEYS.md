# Central AI provider credentials

Administrators can register multiple named API keys for OpenAI, Anthropic and Google Gemini, select one credential per provider, rotate or delete a key, disable a provider and run an explicit synthetic connection test. Credentials are shared by the existing extraction integrations through `apps.core.ai_credentials`; individual module permissions and review/confirmation requirements still apply. A registered provider does not change another provider's configuration or enable unsupported model capabilities.

The [consumer inventory](AI_PROVIDER_CONSUMER_COVERAGE.md) lists the connected application families and verification limits. Email AI and Ask RADAI resolve the selected central key for their configured provider; their existing module model setting remains an explicit override. Planning uses the selected compatible project provider and honors explicit project disable, while new projects can use the central connection without saving a project key. Legacy BYOK feature flags govern unmanaged compatibility, not central administrator activation. Planning's sequence proposal cannot switch to a personal or different-provider connection when its configured provider is centrally managed but unavailable.

## Storage and deployment

Apply `core.0013_ai_provider_credentials` before using the registry. It creates `AIProviderCredential` and `AIProviderConfiguration`, without copying environment credentials or modifying existing business data. Local and production databases and encryption settings are separate.

Set a strong, persistent `AI_CREDENTIAL_ENCRYPTION_KEY` in backend and worker secrets. An explicitly configured `BYOK_ENCRYPTION_KEY` is the compatibility fallback; Django `SECRET_KEY` is never used. API keys are Fernet encrypted with a SHA-256-derived encryption key. Preserve the encryption material with the database backup. Replacing that material without re-encrypting the stored credentials makes existing values unreadable. No encryption secret is generated by the application or returned through the API.

The administrator overview reports `encryption_ready`. Missing encryption prevents key registration, rotation, decryption and testing. Listing safe metadata and disabling a provider remain possible. No plaintext, ciphertext, key suffix or key prefix is returned. Provider keys should only be entered into the administrator form, never in logs, source control or support messages.

Rolling back migration 0013 deletes the new configuration tables and their stored credentials; the reverse/reapply test only certifies schema reversibility on a disposable database. Back up configuration before an operational rollback. Deploy the schema before code that resolves registry credentials, since a missing table fails closed.

## Resolution rules

`resolve_provider_credential(provider, fallback='')` returns the key and safe metadata from one joined database read. `get_provider_api_key` returns its key; `get_provider_configuration` returns safe metadata only. Call at operation time after Django startup, with no process-global key cache. A callable fallback is evaluated only when that provider has no central configuration row.

- A provider with no central configuration can use its module's existing environment or legacy credential.
- A managed provider uses only its selected, enabled credential while the provider is enabled.
- Disabling a provider or its selected credential, deleting its selected credential, or having no selected credential yields no key. It does not switch credentials or revive an environment value.
- Database, registry-startup and encryption failures raise the sanitized `AICredentialUnavailable`. They never trigger legacy fallback.
- A provider configuration row remains after its last key is deleted, preserving the administrator's managed policy.
- Model bindings remain explicit. Consumers that support a saved provider model use that binding; integrations with a specialized model contract retain their supported configuration. A synthetic connection success does not certify every extraction schema or model capability.

Consumers must bind a resolved managed credential to its official provider host and prevent unrelated ambient account/authentication settings from overriding the selected key. The shared lazy SDK clients use the resolver's matching key/metadata snapshot for this purpose.

## Administrator contract

Base: `/api/v1/rbac/admin/ai-api-keys/`. Requires an active Django user, an active, unlocked, non-deleted RBAC profile, and Django superuser or an active `super_admin`, `admin` or `ict_admin` role. Existing `admin_dashboard` action permissions apply separately. `is_staff` alone is insufficient. All responses use `Cache-Control: private, no-store`.

GET returns `encryption_ready`, `providers` and `credentials`. Provider metadata includes `provider`, `managed`, `enabled`, `model`, `key_configured`, `revision`, `selected_credential_id`, `encryption_ready`, `ready`. Credential metadata includes `id`, `provider`, `label`, `enabled`, `is_selected`, `revision`, timestamps and `last_tested_at`, `last_test_status`, `last_test_reason`, `last_test_model`. Test status is empty, `passed` or `failed`. Readiness means configuration is present, not successful provider authentication.

| Method and relative route | Input |
| --- | --- |
| POST base | `provider`, `label`, `api_key`, `expected_provider_revision`; optional `enabled`, `model` |
| PATCH `{id}/` | `expected_revision`, `expected_provider_revision`; optional `label`, replacement `api_key`, `enabled` |
| DELETE `{id}/` | `expected_revision`, `expected_provider_revision` |
| POST `{id}/select/` | `expected_revision`, `expected_provider_revision` |
| PATCH `providers/{provider}/` | `expected_revision`; optional `enabled`, `model` |
| POST `{id}/test/` | `expected_revision`, explicit `model` |

Absent provider revision is `0`. The first registered credential selects itself. Registering or selecting another credential does not re-enable a disabled provider. Omitting `api_key` on PATCH keeps the saved key; blank replacement is rejected. Model changes for an existing provider use its settings endpoint. Unknown fields, unrecognized providers, malformed models and noninteger revisions are rejected. Writes return a fresh overview; create returns 201. Stale writes return 409 with `ai_credentials_stale`. State and metadata-only audit records commit in the same transaction; failed audit persistence rolls the write back.

Active authenticated users may GET `/api/v1/rbac/ai-provider-status/`. Its only projection is `{providers: [{provider, managed, enabled, ready, model}]}`. It does not disclose credential identifiers, labels, counts, storage configuration or audit history. It grants no extraction, source-document or job permissions.

## Synthetic connection test

The explicit administrator test sends a fixed prompt requesting `{"ok": true}` to the selected official provider with a saved key and explicit model. It sends no emails, uploaded documents, questions or business data. It uses a bounded 1024-token output, a 20-second provider timeout (Gemini also uses a 5-second connect timeout), and no SDK retries. A per-administrator cache lease rejects duplicate concurrent tests; cache failure prevents dispatch. A rotated/deleted key or stale revision prevents the old result from being saved.

Test responses add `test: {success, reason, model}` to the overview. A completed provider rejection returns HTTP 200 with `success: false`; a concurrent test returns 429 `test_in_progress`; registry/storage errors return sanitized 503. Provider errors and SDK/http transport logs are not returned or persisted. Static allowlisted reasons are:

`provider_authentication`, `provider_permission`, `provider_rate_limit`, `provider_request`, `provider_timeout`, `provider_unavailable`, `provider_dependency_missing`, `invalid_response`, `credit_balance_exhausted`, `model_unavailable`, `request_configuration_error`, `provider_incomplete`, `provider_refused`.

Known credit/model/request-configuration rejections are mapped from bounded provider error categories to these static values; raw error bodies are not exposed. Success verifies only that the selected provider accepted this synthetic request and returned the expected JSON. It does not guarantee every extraction module, deployment, provider account quota or future request will succeed.

## Verification

The registry and probe suite runs with `python manage.py test apps.core.tests.test_ai_credentials --settings=config.settings_release_test --noinput` in a disposable container using in-memory SQLite, synthetic encryption/keys, mocked provider SDKs and no network. Its tests cover lifecycle, selected-provider isolation, immediate rotation/disable, legacy precedence, lazy fallback, write revisions, atomic audit failure, administrator roles and separate action denials, request-audit privacy, ordinary-user projections, bounded provider requests, sanitized failures and stale/concurrent connection tests.

Migration checks use a separate disposable PostgreSQL 16 database with no application volumes or public network access. They compare core migration state, replay the core chain through 0013, verify selected-key deletion blocks fallback, reverse 0013 to 0012 and reapply 0013. These checks do not claim a production migration or a real provider connection was performed.

Local verification on 30 September 2026: 224 combined backend tests passed in the Python 3.11 production image with provider networking disabled; 32 frontend browser cases and the Node 20 production build passed. Core0013 was applied locally after the disposable migration checks. Backend, worker and scheduler were healthy after restart and used the same local encryption configuration. All 119 changed/new Python files parsed; the changed-file fatal lint scan retained 24 findings from HEAD with zero new findings. Existing frontend lint and bundle-size warnings remain documented in the feature brief. These changes are local and have not been deployed to production.
